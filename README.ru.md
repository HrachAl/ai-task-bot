# AI Task Bot

[English version](README.md)

Омниканальный менеджер задач: отправляешь Telegram-боту текстовое или голосовое
сообщение — и задача мгновенно появляется на Kanban-доске. Голосовые сообщения
расшифровываются Whisper асинхронно, через Celery-воркер, поэтому бот никогда не
зависает в ожидании OpenAI. У каждого Telegram-аккаунта своя приватная доска, а
изменения с любой стороны — из бота или с доски — синхронизируются друг с другом по
WebSocket в реальном времени.

```
Telegram текст  → FastAPI → PostgreSQL ─────────────────────┐
                                                              ├─→ WebSocket → React
Telegram голос  → FastAPI → Redis/Celery → Worker → Whisper ─┘
                                           → PostgreSQL
```

Это тестовое задание на стажировку. Объём намеренно ограничен небольшим, но
доведённым до ума MVP, а не корпоративным клоном таск-трекера: нет ролей, меток,
приоритетов, подзадач, вложений и центра уведомлений. Контроль доступа тоже
намеренно минимален — персональный токен, который выдаёт бот, а не полноценная
система аккаунтов (обоснование архитектуры — в [PLAN.md](PLAN.md)).

## Архитектура

Шесть контейнеров, три из которых собираются из одного Python-образа:

| Сервис | Роль | С кем общается |
|---|---|---|
| `bot` | aiogram long polling — только ввод-вывод Telegram | Telegram API, `backend` (HTTP) |
| `backend` | FastAPI REST API + WebSocket-сервер; применяет миграции при старте | PostgreSQL, Redis |
| `worker` | Celery-воркер — пайплайн расшифровки голоса | PostgreSQL, Redis, Telegram API, OpenAI |
| `frontend` | React-доска, собранная и отдаваемая через nginx | `backend` (через прокси, тот же origin) |
| `postgres` | Постоянное хранилище — единственный источник правды | — |
| `redis` | Брокер Celery **и** шина событий pub/sub | — |

Система держится на двух правилах:

1. **Бот никогда не обращается к Postgres или Redis напрямую.** Он говорит с
   `backend` только по HTTP (`POST /api/tasks`, `POST /api/tasks/voice`). Благодаря
   этому бот остаётся тонким, легко тестируемым слоем ввода-вывода, а все записи
   принадлежат бэкенду.
2. **Вся real-time рассылка идёт через один канал Redis pub/sub** (`task_events`, на
   отдельной логической базе Redis — не той, где брокер Celery). Кто бы ни изменил
   задачу — `backend` при создании текстовой задачи и смене статуса, `worker` после
   завершённой расшифровки — публикует событие туда. `backend` единственный держит
   живые WebSocket-соединения и рассылает то, что получил. Именно поэтому **воркер в
   совершенно другом процессе** может обновить картинку в браузере.

### Текстовый поток
`Telegram текст → бот → POST /api/tasks → коммит в PostgreSQL → публикация → WebSocket → React`

### Голосовой поток
`Telegram голос → бот → POST /api/tasks/voice (202, в базу ещё ничего не записано)
→ Celery/Redis → воркер скачивает файл → Whisper → коммит в PostgreSQL → публикация
→ WebSocket → React`

Строка `Task` не появляется, пока расшифровка не завершилась успешно: неудачная или
пустая расшифровка не оставляет за собой частичных данных, а бот редактирует своё же
сообщение-заглушку «🎤 расшифровываю…», подставляя туда итоговый результат (или
понятное сообщение об ошибке).

И к текстовому, и к голосовому подтверждению прикрепляется inline-клавиатура
(Pending / In Progress / Completed). Нажатие кнопки вызывает тот же
`PATCH /api/tasks/{id}`, что и drag-and-drop на доске, поэтому смена статуса
доезжает до доски, не выходя из Telegram.

### Управление задачами из Telegram
`/list` возвращает задачи вызывающего в виде списка кнопок. Открытая задача
показывает свои детали (заголовок, описание, статус, id, время создания) вместе с
кнопками статуса, кнопкой удаления и кнопкой возврата — то есть задачей можно
управлять изнутри неё самой, а не только из сообщения, которым она была создана. Бот
редактирует одно сообщение вместо того, чтобы добавлять новые, поэтому чат ведёт себя
как небольшое приложение с экранами.

Удаление сначала спрашивает подтверждение — это единственное необратимое действие,
которое предлагает бот, а inline-кнопки стоят прямо под сообщением. Поскольку задачу
можно удалить с любой стороны, удаление публикуется в realtime-канал как
`task_deleted`, и открытая доска убирает карточку немедленно.

### Отдельная доска для каждого пользователя
У каждого Telegram-аккаунта своя доска, без формы регистрации и без пароля:
идентификатором служит сам Telegram-аккаунт. В каждой строке `users` хранится
случайный `access_token`, а `/dashboard` отвечает персональной ссылкой
(`https://<доска>/?token=…`). Браузер сохраняет токен, убирает его из адресной
строки и дальше отправляет в заголовке `Authorization: Bearer …` — а на рукопожатии
WebSocket, которое не умеет нести заголовки, параметром `?token=`.

Отсюда следуют два свойства:

- **Ограничение по владельцу проверяется на сервере, в одном месте.** Ни один
  эндпоинт не читает id владельца из тела запроса — он всегда берётся из учётных
  данных вызывающего. Чужая задача возвращает `404`, а не `403`, потому что `403`
  подтвердил бы, что такой id существует на другой доске.
- **Realtime-канал ограничен так же.** Каждый WebSocket запоминает пользователя,
  который его открыл, а слушатель Redis маршрутизирует события по `user_id` из
  полезной нагрузки.

Персонального токена у бота нет. Он аутентифицируется как внутренний сервис
(`X-Internal-Token`) и называет Telegram-пользователя, от имени которого действует
(`X-Telegram-Id`); бэкенд разрешает эту пару в аккаунт, создавая его при первом
контакте.

## Стек технологий

**Бэкенд** — Python 3.12, FastAPI, SQLAlchemy 2.x (async), Alembic, Pydantic v2,
aiogram 3, Celery 5 + Redis, OpenAI SDK (Whisper), pytest.
**Фронтенд** — React 18, TypeScript, Vite, `@dnd-kit` для drag-and-drop, CSS Modules
с небольшой системой дизайн-токенов (по умолчанию светлая тема, в шапке —
переключатель светлой/тёмной, сохраняемый между сессиями); без стейт-менеджера и без
CSS-фреймворка.
**Инфраструктура** — Docker, Docker Compose, nginx (отдаёт собранный фронтенд и
проксирует `/api` и `/ws` на бэкенд — тот же origin, поэтому в продакшене CORS не
нужен вовсе).

## Запуск

**Требуется:** Docker и Docker Compose. Больше ничего — Postgres, Redis и все
рантаймы работают внутри контейнеров.

```bash
cp .env.example .env
# добавьте TELEGRAM_BOT_TOKEN и OPENAI_API_KEY, чтобы бот работал по-настоящему;
# REST API, доска и WebSocket работают и без них (см. «Настройка Telegram-бота»)

docker compose up --build
```

Затем откройте доску: она попросит подключить Telegram. Отправьте боту `/dashboard`
и перейдите по ссылке, которую он пришлёт.

- Доска: **http://localhost:3001**
- Документация API (Swagger UI): **http://localhost:8001/docs**
- Health check: **http://localhost:8001/api/health**

(`8001` и `3001` — это только порты на стороне хоста; внутри Docker-сети `backend`
по-прежнему слушает `8000`, а nginx — `80`. Они были сдвинуты, чтобы не конфликтовать
с тем, что уже занято на хосте.)

Доска загружает список задач через `GET /api/tasks` при первой отрисовке, дальше
синхронизацию держит WebSocket (`/ws/tasks`, проксируется nginx) — без опроса и без
ручного обновления. Цветная точка в шапке показывает состояние соединения (зелёная —
на связи, янтарная — переподключается), а клиент переподключается с экспоненциальной
задержкой при обрыве.

## Переменные окружения

Все переменные лежат в одном файле `.env` в корне репозитория (полный
прокомментированный список — в `.env.example`). Главные:

| Переменная | Назначение |
|---|---|
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | Учётные данные Postgres — используются и для инициализации контейнера, и для сборки `DATABASE_URL` |
| `DATABASE_URL` | Асинхронный URL SQLAlchemy, который использует бэкенд и Alembic |
| `REDIS_URL` | Брокер Celery + бэкенд результатов |
| `REDIS_PUBSUB_URL` / `TASK_EVENTS_CHANNEL` | Шина realtime-событий (намеренно отдельная логическая база Redis, тот же инстанс) |
| `TELEGRAM_BOT_TOKEN` | От [@BotFather](https://t.me/BotFather) — без него бот не работает |
| `MAX_VOICE_DURATION_SECONDS` / `MAX_VOICE_FILE_MB` | Бот отклоняет слишком длинные и тяжёлые голосовые до того, как задача попадёт в Redis/Celery |
| `OPENAI_API_KEY` | Нужен для настоящей расшифровки |
| `WHISPER_MODEL` / `WHISPER_LANGUAGE` | По умолчанию `whisper-1` и автоопределение языка |
| `BACKEND_INTERNAL_URL` | Как контейнер `bot` достаёт `backend` (`http://backend:8000` внутри Docker) |
| `INTERNAL_API_TOKEN` | Общий секрет, позволяющий боту действовать от имени Telegram-пользователя. Значение в `.env.example` — заглушка для локальной разработки, **перед деплоем сгенерируйте настоящее** (см. «Развёртывание») |
| `DASHBOARD_BASE_URL` | Публичный адрес доски; из него бот собирает каждую ссылку `/dashboard` |
| `CORS_ORIGINS` | Имеет значение, только если фронтенд-дев-сервер запущен отдельно от nginx |

Без `TELEGRAM_BOT_TOKEN` и `OPENAI_API_KEY` работает всё, **кроме самого бота**: REST
API, WebSocket, доска и воркер (он просто аккуратно упадёт на вызовах Telegram/OpenAI
с повторами и понятным сообщением об ошибке) полностью пригодны для локальной
проверки.

### Настройка Telegram-бота

1. Напишите [@BotFather](https://t.me/BotFather) в Telegram, выполните `/newbot`,
   следуйте подсказкам.
2. Скопируйте выданный токен в `.env` как `TELEGRAM_BOT_TOKEN`.
3. `docker compose up -d --build bot` (или просто перезапустите
   `docker compose up --build`).
4. Напишите своему боту: обычный текст сразу становится задачей; на голосовое придёт
   мгновенный ответ «🎤 расшифровываю…», и это же сообщение будет отредактировано на
   месте, когда Whisper закончит.

Бот использует **long polling**, а не вебхуки — для локального запуска не нужны ни
публичный адрес, ни ngrok, ни TLS-сертификат.

### Настройка OpenAI / Whisper

Укажите `OPENAI_API_KEY` в `.env`. Это единственный обязательный шаг:
`WHISPER_MODEL` по умолчанию `whisper-1`, а `WHISPER_LANGUAGE` оставлен пустым для
автоопределения. Расшифровка спрятана за небольшим протоколом `Transcriber`
(`backend/app/integrations/transcriber.py`), поэтому тесты проверяют реальную логику
пайплайна на фейковой реализации, а не ходят в OpenAI.

## Запуск в Docker

`docker compose up --build` собирает и стартует в порядке зависимостей:

1. `postgres` и `redis` (у каждого настоящий healthcheck — `pg_isready` и
   `redis-cli ping`; всё остальное ждёт именно их готовности, а не просто «запущен»)
2. `backend` — ждёт postgres и redis, **автоматически выполняет
   `alembic upgrade head`**, затем запускает uvicorn; имеет свой healthcheck
   (`GET /api/health`)
3. `worker` и `frontend` — ждут, пока `backend` станет healthy
4. `bot` — тоже ждёт `backend`; требует валидный `TELEGRAM_BOT_TOKEN`, иначе сразу
   завершается (это ничего не блокирует — REST API, доска и воркер полностью
   независимы от бота)

`backend`, `worker` и `bot` — это **один Docker-образ** (`backend/Dockerfile`),
запущенный с тремя разными командами: общий код, три деплоя. `worker` и `bot`
пропускают шаг миграций из образа (переопределение `entrypoint: []` в
`docker-compose.yml`), поэтому миграции выполняются ровно один раз — из `backend`.

Порты, опубликованные на хост: **3001** (доска) и **8001** (API). Postgres и Redis
доступны только во внутренней Docker-сети и наружу не публикуются, потому что
напрямую к ним ничему снаружи обращаться не нужно.

## Миграции базы данных

Миграции Alembic лежат в `backend/alembic/versions/`: начальная схема создаёт `users`
и `tasks`, вторая добавляет `users.access_token`. Они выполняются автоматически при
каждом старте контейнера `backend` (`backend/entrypoint.sh` → `alembic upgrade head`,
до запуска uvicorn) — воспроизводимо по построению: свежий `docker compose up --build`
всегда приводит к одной и той же схеме, а повторный запуск идемпотентен, если схема
уже на последней ревизии.

Запустить миграции вручную (например, против локального Postgres вне Docker):

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
# укажите DATABASE_URL в backend/.env, чтобы он смотрел на ваш Postgres
alembic upgrade head
```

## Как работает воркер

Celery-воркер (`backend/app/worker/tasks.py`) владеет всем голосовым пайплайном,
чтобы обработчик Telegram в боте никогда не блокировался:

1. Бот проверяет ограничения по длительности и размеру, сразу отвечает
   «🎤 расшифровываю…», затем вызывает `POST /api/tasks/voice` — который ставит
   задание в очередь Celery и возвращает `202`, **ещё ничего не записав в базу**.
2. Воркер скачивает голосовой файл из Telegram, отправляет его в Whisper и только
   *после этого* создаёт строку `Task` — поэтому в Postgres лежат только успешно
   расшифрованные задачи, без частичных.
3. Он публикует событие `task_created` и редактирует сообщение-заглушку бота,
   подставляя итоговый текст.

**Обработка отказов** настроена по типу ошибки (`backend/app/exceptions.py` +
`backend/app/worker/tasks.py`):

| Отказ | Поведение |
|---|---|
| Ошибка скачивания из Telegram, временный сбой Whisper/OpenAI | Автоматический повтор (`autoretry_for`, экспоненциальная задержка, джиттер, максимум 3 попытки) |
| Пустое или битое аудио, тишина в записи | Отказ сразу — повторять непригодный файл бессмысленно, поэтому такие ошибки исключены из `autoretry_for` |
| Попытки исчерпаны или ошибка неповторяемая | Бот редактирует заглушку понятным сообщением об ошибке (`⚠️ Couldn't transcribe...`) через хук Celery `on_failure`, который срабатывает ровно один раз |

И подтверждение успеха, и сообщение об ошибке доставляются отдельной Celery-задачей
`notify_telegram` (`notify_telegram_task`), а не прямым вызовом Telegram API — так
что временный сбой сети или Telegram *в момент отправки самого уведомления* тоже
повторяется (3 попытки, экспоненциальная задержка) через ту же очередь Redis, а не
теряется молча.

Настройка `task_acks_late=True` означает, что сообщение удаляется из Redis только
после успешного завершения работы: если процесс воркера убили посреди задания, оно
будет доставлено заново, а не потеряно (стандартный компромисс at-least-once для
очереди задач — см. «Известные ограничения»).

## Как работают обновления в реальном времени

- `backend` держит `ConnectionManager` (`backend/app/realtime/manager.py`) — живые
  WebSocket-соединения на `/ws/tasks`, каждое вместе с id пользователя, который его
  открыл. Соединение, не сумевшее принять сообщение (клиент уже ушёл), отбрасывается,
  а не ломает рассылку для остальных.
- Фоновая задача в lifespan бэкенда подписана на канал Redis pub/sub и пересылает
  каждое сообщение через `ConnectionManager`, маршрутизируя его по `user_id` из
  полезной нагрузки, чтобы событие дошло только до того аккаунта, которому
  принадлежит. В этот канал публикуют и код обработки запросов (создание текстовых
  задач, смена статуса, удаление), и отдельный Celery-воркер (завершённые
  расшифровки) — это единственная причина, по которой воркер в другом процессе может
  обновить чей-то браузер.
- Каждый путь публикации обёрнут так, чтобы сбой Redis не мог провалить запрос,
  который уже закоммичен в Postgres. Realtime-слой — удобство, а не зависимость:
  WebSocket отвечает только за синхронизацию.
- На фронтенде `useTaskSocket` переподключается с экспоненциальной задержкой
  (1с → 15с) и пересинхронизирует список задач после каждого успешного
  переподключения. Входящие события сливаются по принципу upsert-by-id
  (`useTasks.upsertTask`): заменить, если id уже есть, иначе добавить в начало.
  Поэтому дубликат или пришедшее не по порядку событие не могут породить вторую
  карточку, а ответ REST и эхо того же изменения по WebSocket проходят один и тот же
  путь.

## Drag-and-drop и смена статуса

Перетаскивание карточки в другую колонку (`@dnd-kit`) обновляет локальное состояние
**оптимистично**, затем вызывает `PATCH /api/tasks/{id}`. Если запрос не удался,
доска возвращается к снимку до перетаскивания, а тост объясняет, что произошло;
проверено headless-браузерным тестом, который принудительно роняет вызов `PATCH` и
проверяет и откат, и тост.

## Как тестировать

**Бэкенд** — 149 тестов (`pytest`), база не мокается: настоящий Postgres (отдельная
база `*_test`), каждый тест изолирован в откатываемой транзакции/сейвпоинте.
Покрыто: CRUD задач и валидация, изоляция досок между пользователями и аутентификация
(bearer-токен и внутренний вызов бота), успешные и неуспешные пути голосового
пайплайна (сбой скачивания, битое аудио, ошибка расшифровки, пустой результат) с
фейковыми клиентами Telegram и Whisper, конфигурация повторов Celery и уведомление об
ошибке, публикация realtime-событий (в том числе что сломанный Redis никогда не
ломает запрос), маршрутизация событий по пользователю, WebSocket-эндпоинт против
настоящего Redis, экраны бота (`/list`, карточка задачи, подтверждение удаления) и
два регрессионных теста на состояние гонки при создании пользователя.

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
# укажите в backend/.env адреса Postgres и Redis (docker run postgres:16-alpine /
# redis:7-alpine вполне подойдут — создайте базу `<db>_test` рядом с основной)
alembic upgrade head
pytest
```

**Фронтенд:**

```bash
cd frontend
npm install
npm run typecheck   # tsc -b --noEmit
npm run build        # продакшен-сборка
```

**End-to-end, с чистого клона:**

```bash
cp .env.example .env   # добавьте TELEGRAM_BOT_TOKEN и OPENAI_API_KEY, чтобы проверить бота
docker compose up --build
```

1. Откройте http://localhost:3001 — экран подключения Telegram. Отправьте боту
   `/dashboard` и перейдите по ссылке: откроется пустая доска с зелёным индикатором
   «Live».
2. Нажмите **New Task**, введите заголовок, отправьте — задача появится на доске
   мгновенно, без перезагрузки.
3. Напишите боту в Telegram: обычный текст → задача появляется на доске за секунду.
   Голосовое → сразу появляется заглушка «расшифровываю…», которая обновляется на
   месте текстом расшифровки, когда Whisper закончит; сообщение в Telegram
   редактируется соответственно.
4. Перетащите карточку между колонками — статус переживает перезагрузку страницы.
5. Откройте вторую вкладку браузера — создайте задачу в одной и посмотрите, как она
   появляется в другой.
6. Кликните по карточке → смените статус или удалите её из панели деталей.
7. Отправьте боту `/list` → откройте задачу → смените статус изнутри неё; карточка
   переедет на доске одновременно. Удалите её из бота → карточка исчезнет с открытой
   доски без обновления.
8. Отправьте `/dashboard` → откройте ссылку в приватном окне → загрузятся только ваши
   задачи. Напишите боту со второго Telegram-аккаунта и убедитесь, что его задачи
   никогда не появляются на доске первого (и на его WebSocket тоже).

## Развёртывание

Помимо `TELEGRAM_BOT_TOKEN` и `OPENAI_API_KEY`, для любого развёртывания, доступного
не только с `localhost`, обязательно задать две переменные:

```dotenv
# Адрес, по которому пользователи реально открывают доску. Из него бот собирает
# каждую ссылку /dashboard, поэтому устаревшее значение даёт ссылки в никуда.
DASHBOARD_BASE_URL=https://your-domain.example

# Сгенерируйте новый: openssl rand -hex 24
INTERNAL_API_TOKEN=<случайный>
```

С точки зрения безопасности важен именно `INTERNAL_API_TOKEN`. Он позволяет своему
владельцу действовать от имени любого Telegram-пользователя, а nginx отдаёт `/api` на
том же origin, что и доску — значит, он доступен везде, где доступна доска, а не
только внутри Docker-сети. Оставить в публичном развёртывании заглушку из
`.env.example` равносильно тому, чтобы оставить открытыми все доски.

Публиковать нужно только порт `frontend`; nginx проксирует `/api` и `/ws` на
`backend` внутри Docker-сети. За обратным прокси пробрасывайте хост и заголовки
апгрейда WebSocket — у Caddy обычный `reverse_proxy` делает и то, и другое.

## Известные ограничения (осознанные решения по объёму)

- **Доступ по токену, а не управление аккаунтами.** Доступ — это один bearer-токен на
  пользователя, который выдаёт бот. Намеренно нет ни пароля, ни email, ни срока
  жизни сессии, ни эндпоинта ротации: сложная аутентификация была исключена из
  объёма, а идентичностью уже владеет Telegram. Токен — это весь credential целиком,
  поэтому у любого, кому переслали ссылку, будет такой же доступ. В продакшене я бы
  добавил ротацию и отзыв.
- **`INTERNAL_API_TOKEN` необходимо сменить перед развёртыванием.** Он позволяет
  действовать от имени любого Telegram-пользователя, а nginx проксирует `/api` рядом
  с доской, поэтому он доступен везде, где доступна доска. Значение в `.env.example` —
  заглушка для локальной разработки, см. «Развёртывание».
- **At-least-once для голосовых.** `task_acks_late=True` означает, что падение
  воркера в узком окне между коммитом задачи и подтверждением сообщения может
  привести к повторной обработке этого голосового при передоставке. Это стандартный
  осознанный компромисс против альтернативы (потерять задание при падении совсем), и
  на таком масштабе он не должен иметь значения.
- **Нет ручного порядка внутри колонки.** Карточки всегда отсортированы по времени
  создания; перетаскивание карточки обратно в свою же колонку ничего не делает.
  Сохранение ручного порядка потребовало бы отдельной колонки и логики переиндексации,
  которых ТЗ не требует.
